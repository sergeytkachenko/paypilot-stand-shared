# PayPilot — навчальний стенд AI Quality Engineering

AI-агент підтримки необанку **Verta**: перевіряє рахунки й ліміти, рахує
конвертацію валют, відкриває спори, шукає у внутрішній документації.

Це не демо. Це система, у якій **є дефекти** — і ваша робота на курсі полягає
в тому, щоб їх знаходити, доводити прогонами й писати перевірки, які їх
ловлять. Профілі занять вмикають різні набори дефектів, а профіль `clean` —
еталон, з яким усе порівнюється.

## Швидкий старт

> **Піднімаєте вперше — відкрийте [docs/setup.md](docs/setup.md).** Там те
> саме, але з нуля: що встановити, звідки взяти ключ, куди його вписати і як
> переконатися, що все зібралося. Блок нижче — для тих, у кого Docker уже
> стоїть.

```bash
cp -n .env.example .env                            # впишіть ключ провайдера
docker compose up --build -d                       # перший запуск: 5-10 хвилин
docker compose exec stand python scripts/doctor.py # діагностика
```

**Ключ вписується до першого запуску.** `docker-compose.yml` читає всі
налаштування з `.env` під час старту, і за замовчуванням провайдер — `mock`.
Стенд, піднятий без `.env`, стартує успішно й мовчки відповідає заглушками:
жодної помилки ви не побачите. Після зміни `.env` — `docker compose up -d`.

Чат — **http://localhost:8000**. Там перемикач профілів, поштучне вмикання
дефектів, керування часом і дерево спанів останнього ходу. Phoenix (UI
трасування) — **http://localhost:6006**.

Зупинити: `docker compose down`, дані лишаються. Подивитися, на що скаржиться
стенд: `docker compose logs stand`.

> **Не знаєте, з чого почати — почніть із [docs/first-run.md](docs/first-run.md).**
> П'ятнадцять хвилин, одна проходка по циклу: звідки береться еталон, як
> побачити розбіжність і чому правильна відповідь у тексті нічого не доводить.
> Один дефект там розкритий навмисно, щоб ви вчилися інструменту на прикладі
> з відомою відповіддю.

> **Phoenix (UI трасування) стартує повільніше за стенд** — близько хвилини.
> Поки він піднімається, `doctor` показує на ньому `WARN`; повторіть команду
> через хвилину. Трейси від цього не залежать: вони завжди доступні через
> `GET /api/_test/traces/...` і з файлу `traces/traces.jsonl`.

> `.env.example` за замовчуванням ставить `LLM_PROVIDER=mock` — детерміновані
> відповіді без ключа. Годиться, щоб перевірити, що все піднялося. **Не
> годиться** для завдань, де треба показати розподіл відповідей: mock завжди
> відповідає однаково.

## Як розмовляти зі стендом

Єдиний змістовний ендпоінт — `POST /chat`.

```bash
curl -X POST localhost:8000/chat \
  -H 'content-type: application/json' \
  -d '{"session_id": "my-run-1", "message": "I am CUS-0001. What is my balance?"}'
```

```json
{"session_id": "my-run-1", "request_id": "770b66331f4f42fd",
 "answer": "Your balance is ...", "step_number": 1,
 "prompt_version": "base.v1", "elapsed_ms": 2480.3,
 "usage": {"input_tokens": 4791, "output_tokens": 157}}
```

`elapsed_ms` і `usage` — це те, з чим працюють бюджетні вимоги: латентність і
вартість ходу вимірюються без звернення до трейсу.

Чотири речі, які варто знати одразу:

1. **Клієнт називається в тексті повідомлення.** Окремого поля немає: агент
   дізнається, з ким говорить, зі слів `I am CUS-0001`. Не назвете — агент
   перепитає й витратить крок.
2. **`session_id` — це і є діалог.** Той самий рядок продовжує розмову, новий
   починає з чистого аркуша.
3. **Трейс у відповіді не приходить.** Візьміть `request_id` і заберіть дерево
   спанів окремо: `GET /api/_test/traces/<request_id>`. Саме там аргументи й
   результати викликів інструментів — тобто все, чого немає в тексті
   відповіді. Трейси переживають перезапуск стенду.
4. **`POST /api/_test/compare` коштує два виклики моделі**, бо шле запит на
   обидва профілі одразу. Кнопка в чаті робить ще третій, короткий: легка
   модель пояснює різницю (`/api/_test/compare/explain`).

## Поверхні для дослідження

Дефект може не мати сліду в тексті відповіді. Ось де ще можна дивитися.

| Поверхня | Що дає |
|---|---|
| `GET /api/_test/traces/<id>` | дерево спанів: аргументи й результати інструментів, токени, пошукові фрагменти |
| `GET /api/_test/state/{table}` | що реально записано: `disputes`, `statements_sent`, `escalations`, `accounts`, `transactions`, `customers` |
| `GET /api/_test/seed` | версія seed, клієнти, рахунки і **кількість** транзакцій; самі транзакції — `GET /api/_test/state/transactions` |
| `GET /api/_test/prompt` | системний промпт, з яким зараз працює агент |
| `GET /api/_test/specs` | документи вимог (US-01) |
| `GET /api/_test/tools` | схеми інструментів: назви, описи, параметри |
| `app/engines/` | доменні розрахунки: курс, ліміти, вікна оскарження |

**`app/engines/` — це ваш оракул.** Звичайний Python, без агента й без моделі.
Він рахує правильну відповідь однозначно, і його можна імпортувати в тест. Усе,
що ви зможете довести, доводиться порівнянням із ним, а не враженням від тексту.

## Чат-інтерфейс

Усе те саме є мишею, і на занятті зручніше так. Головний екран тримає лише цикл
L01–L03: обрати профіль, поставити питання, порівняти, прочитати вердикт,
скопіювати доказ. Решта відкривається, коли знадобиться:

| Де | Що дає |
|---|---|
| **Профіль** (верхня панель) | перемикач профілю з описом заняття і посилання «Чим відрізняється від clean» — огляд і diff системного промпту проти `clean` (артефакт, який ви аудитуєте) |
| **Як клієнт** (у полі вводу) | від імені якого клієнта питаємо: додає на початок «I am CUS-000X.» (або «Я CUS-000X.» для українського питання); там же seed-дані — клієнти, рахунки, тіри, hold |
| **Як має бути** (з картки порівняння) | еталонні значення рушіїв банку (`app/engines/policy.py`), рядок тіру клієнта підсвічено |
| **Меню › Розширені налаштування** | 27 чипів дефектів (з профілю / увімкнені вами), час прогону, поріг згортки, `top_k` і індекс, стан стенду, дерево трейсу останнього ходу, «Типові налаштування» |
| **Меню** | мова УКР/EN, світла/темна тема, великий шрифт для проєктора, нова сесія, API |
| **Меню › Для лектора** | лише на заблокованому стенді: токен лектора і «Скинути стан» |

Дві речі, які легко пропустити:

- **Змінене не ховається.** Якщо дефект, час, згортка, `top_k` чи індекс
  зсунуті з типового значення, у верхній панелі з'являється жовтий чіп
  «змінено: … · скинути». Побачили його — знайте, що стенд не в базовій
  конфігурації, і ваш результат із чужим не порівняється.
- **«Порівняти»** (Enter) шле той самий запит на `clean` і на обраний профіль,
  обидві руки з нової сесії. Картка починається з вердикту (різні / однакові)
  і списку «Що відрізнялося»: поля **результатів інструментів**, що
  розійшлися, поруч зі значенням із довідника, де воно однозначне. Текст і
  payload розходяться не завжди разом, і список саме про це. Нижче — дві
  відповіді з підсвіткою: закреслене є лише на `clean`, зелене — лише на
  профілі. У згорнутих «Деталях» — таблиця «Умови прогону» (профіль, дефекти,
  версія промпту, сесія, час, індекс пошуку, модель), пояснення легкої моделі
  (`EXPLAIN_MODEL`, якщо порожньо — дефолтна модель провайдера; це думка
  моделі, а не перевірка, на `mock` модель не викликається) і сирі payload-и.
  «Копіювати доказ» кладе в буфер питання, обидві відповіді, трейси й
  розбіжності. «Повторити 5 разів» запускає ×5.
- **«Спитати лише <профіль>» продовжує сесію.** Агент пам'ятає попередні ходи,
  і підпис під полем вводу каже, скільки їх позаду; поки сесія триває, Enter
  теж продовжує її. Перемикання профілю починає нову сесію автоматично —
  історія брудного прогону не потрапляє в чистий.

## Керування стендом (те саме через API)

Налаштування прогону бувають двох рівнів.

**На запит** — заголовок `X-Stand-Settings` з JSON-об'єктом, діє лише для цього
запиту і не чіпає нікого іншого. Саме так працює панель чату: вона тримає ваші
налаштування в браузері й додає заголовок до кожного запиту, тому на спільному
стенді студенти не перемикають профіль один одному.

```bash
curl -s localhost:8000/chat -H 'Content-Type: application/json' \
  -H 'X-Stand-Settings: {"profile":"lesson-02","defects":"D25","top_k":2,"index":"kb_clean","clock":"2026-09-15T10:00:00Z","summarize_after":2}' \
  -d '{"message":"I am CUS-0005. Convert 6000 EUR to USD."}'
```

Поля: `profile`, `defects` (рядок через кому або масив), `top_k` 1..20, `index`
(`kb_clean` | `kb_broken`), `summarize_after` ≥ 1, `clock` (ISO-8601). Невідоме
поле або значення → `400` з поясненням. `GET /health`, `/api/_test/defects`,
`/api/_test/clock`, `/api/_test/retrieval`, `/api/_test/summarize_after`
повертають значення, що діють для цього запиту, і поле `scope`: `request`,
коли заголовок щось задав, інакше `server`.

**На сервер** — PUT-ендпоінти нижче міняють типові значення для всіх, хто
прийшов без заголовка. На локальному стенді одного студента це зручно; на
спільному стенді їх закривають `STAND_LOCK_GLOBAL=1`: тоді вони й
`POST /api/_test/reset` відповідають `403`, а відкриває їх лише заголовок
`X-Stand-Admin` зі значенням `STAND_ADMIN_TOKEN` (у чаті — «Меню › Для лектора»). `/health` показує `locked` і `admin`.

| Ендпоінт | Призначення | Рівень |
|---|---|---|
| `PUT /api/_test/profile` | перемкнути профіль заняття | сервер |
| `GET/PUT /api/_test/defects` | поштучно вмикати дефекти | сервер (GET — ефективні для запиту) |
| `GET/POST /api/_test/clock` | зафіксувати «поточний» час | сервер (GET — ефективні для запиту) |
| `GET/PUT /api/_test/summarize_after` | після якого кроку історія згортається | сервер (GET — ефективні для запиту) |
| `GET/PUT /api/_test/retrieval` | `top_k` і індекс пошуку; `requested_*` — що задано, `top_k`/`index` — що діє (D17 примусово ставить `top_k=1`, D16 — `kb_broken`) | сервер (GET — ефективні для запиту) |
| `POST /api/_test/reset` | повернути дані до seed | сервер |
| `POST /api/_test/compare` | той самий запит на `clean` і на профілі, поруч; обидві руки з нових сесій, глобальний стан і чужі сесії не чіпає | запит |
| `POST /api/_test/series` | `{"message", "runs" ≤ 5, "profile"?}` — N прогонів із нових сесій на поточних налаштуваннях і, з `profile`, ще N на ньому; для кожного прогону `tools_called`, разом `tool_counts`. Кнопка «Повторити 5 разів» на картці порівняння. Одночасно виконуються щонайбільше дві серії, третя отримує `503` | запит |
| `POST /api/_test/compare/explain` | смислове пояснення різниці двох рук від легкої моделі (`EXPLAIN_MODEL`) | запит |

`LLM_TEMPERATURE` порожнє = температура провайдера за замовчуванням; `0`
звужує розкид відповідей, але зсуває відкалібровані частоти дефектів, тож
міняти її варто лише разом із перекалібруванням каталогу.

**Маршрутизатор `ROUTER=jev`** (типово вимкнений). Перед першим ходом сесії
класифікатор Jev від TypeSafe (`TYPESAFE_API_KEY`, `TYPESAFE_MODEL`) визначає
намір клієнта. Якщо впевненість не нижча за `ROUTER_MIN_CONFIDENCE` (0.9),
агент отримує додатковий блок інструкцій: для тарифу переказу й вікон спору —
значення з `app/engines/policy.py`, для решти намірів — який інструмент
викликати першим. Діє лише на профілях з `ROUTER_PROFILES` (типово `clean`),
тож профілі заняття працюють без нього. Тайм-аут 1 с на кожну фазу запиту
(з'єднання, читання); після трьох помилок поспіль маршрутизатор пропускається
60 с, і хід іде як звичайно. У трейсі — спан `router.jev` з наміром,
впевненістю й доданим текстом; у `/health` і в умовах «clean vs профіль» —
поле `router`. Версія промпту (`base.v1`) не змінюється: доданий блок видно
лише у трейсі.

Увімкнений маршрутизатор надсилає перше повідомлення кожної сесії на
маршрутизованих профілях у `api.typesafe.ai` без змін. Дані стенду вигадані;
для справжніх клієнтських даних це сторонній обробник, і його треба погодити.

**Фіксуйте час.** `CLOCK_OVERRIDE=2026-09-15T10:00:00Z` — еталонна «поточна»
дата, відносно якої підібрані всі транзакції. З реальною датою частина
сценаріїв «поїде», і ваші результати перестануть відтворюватися.

**Скидайте стан.** Після завдань, де ви відкривали спори чи надсилали виписки,
`POST /api/_test/reset` повертає дані до вихідних.

## Відтворюваність

Прогін, який не можна повторити, — не доказ. Щоб результат був відтворюваним,
у записі прогону мають бути зафіксовані:

- **профіль і активні дефекти** — `GET /health` або корінь трейсу
  (`run.profile`, `run.active_defects`);
- **версія промпту** — `prompt.version` у корені трейсу;
- **час** — `GET /api/_test/clock`;
- **модель** — `gen_ai.request.model` на спанах `llm.call`;
- **стан даних** — чи робився `reset` перед прогоном.

Імовірнісна поведінка — це нормально. Та сама модель на той самий запит не
завжди відповідає однаково. Тому одиничний прогін нічого не доводить: пишіть
**розподіл** («у 4 з 5 прогонів…»), а не вердикт.

## Структура

```
app/            стенд: агент, інструменти, доменні рушії, RAG, трейсинг
  engines/      джерело істини — звичайний Python, тестується без агента
  agent/loop.py цикл оркестрації: модель → інструмент → модель
  rag/          індекс і пошук по внутрішній документації
prompts/        системний промпт агента
specs/          документи вимог
profiles/       які набори дефектів вмикає кожне заняття
scripts/        doctor (діагностика), ci_smoke (перевірка поверхонь)
tests/          тести стенду — приклад того, як писати перевірки
```

## Що робити, коли не працює

**`doctor` каже `provider: mock`, хоча ключ вписаний.** Файл має називатися
саме `.env` (не `.env.txt`) і лежати в корені. Рядок — `LLM_PROVIDER=anthropic`
без пробілів навколо `=`. Змінна середовища з консолі перебиває `.env`.

**`HTTP 400` на кожен запит.** Найчастіше — вичерпаний баланс провайдера.
`docker compose exec stand python scripts/doctor.py` перекладе повідомлення
провайдера людською мовою.

**Дефект не проявляється.** Спершу перевірте `GET /health` — чи той профіль
увімкнений. Потім повторіть запит кілька разів: частина дефектів імовірнісна.
Потім подивіться в трейс, а не в текст: дефект може бути в результаті
інструмента, тоді як текст відповіді виглядає правильним. І порівняйте з
`clean` — якщо відповіді на обох профілях однакові, ви дивитеся не туди.

**Дані «зламані».** «Скинути стан» у «Меню › Розширені налаштування» (на
заблокованому стенді — у «Для лектора»), або
`POST /api/_test/reset`.

**Перевірити, що стенд цілий.**
`docker compose exec stand python scripts/ci_smoke.py` — усі поверхні мають
відповісти.

**Сторінка не відкривається.** `docker compose ps` — обидва контейнери мають
бути `Up`; якщо ні, причину покаже `docker compose logs stand`.
