# 0001. Поточний клієнт — контекст сесії, агент дізнається його через get_account

## Status

Accepted, 2026-10-08. Issue #17.

## Context

Чат дописував на початок питання «I am CUS-000X.» (або «Я CUS-000X.»), а агент
сам вписував `customer_id` в аргументи `get_account`, `quote_fx`,
`check_limits`, `escalate_to_human`. Мок-провайдер теж брав id регуляркою з
тексту. Особа клієнта визначалася словами в повідомленні: будь-який текст із
чужим `CUS-…` змінював, чиї дані бачить агент, а серія ×5 показувала, що агент
рахує обмін без `get_account`, бо клієнт уже «відомий» з тексту.

У справжньому банку клієнт приходить у розмову вже автентифікованим, і агент
бере його з контексту сесії. Аудитований `prompts/base.v1.md` §3 і так вимагає:
«Customer-specific data — balances, tier, transactions — must always be
resolved through tools, never assumed».

## Decision

1. Клієнт — властивість сесії. `/chat`, `/api/_test/compare`,
   `/api/_test/series` приймають `customer_id`; це **симульований вхід
   демо-стенду, не автентифікація** — стенд навчальний і облікових записів
   клієнтів не має. Невідомий id → `400`. Клієнт фіксується на першому ході
   сесії, зокрема «без клієнта»: інший `customer_id` для тієї ж сесії → `409`.
2. На час ходу клієнт лежить у `ContextVar` (`app/session_ctx.py`, `bind` зі
   скиданням у `finally`), як налаштування ходу в `app/runctx.py`. Атрибут
   трейсу `session.customer_id`.
3. `get_account` не має параметра `customer_id`: повертає клієнта сесії
   (`customer: {id, name, tier}`) і його рахунки. Решта клієнтських
   інструментів зберігає `customer_id` у схемі, а `tools.dispatch` відмовляє,
   якщо він не збігається з клієнтом сесії або клієнта немає. Тож id агент
   може взяти лише з `get_account`. Інструменти з `account_id` чи
   `transaction_id` (`get_transactions`, `send_statement`, диспути) так само
   працюють лише з рахунками й транзакціями клієнта сесії.
4. Текст повідомлення особу не визначає, фолбеку на `CUS-…` у тексті немає.
   Чат передає вибраного клієнта як `customer_id`; зміна клієнта починає нову
   сесію.
5. Підказки моделі — в описах інструментів, `prompts/base.v1.md` не змінюється
   (`prompt_version` лишається `base.v1`).

## Consequences

- На питання про обмін, ліміти чи ескалацію агент робить на один виклик
  більше: `get_account` перед основним інструментом. У ×5 це видно як
  `get_account 5 з 5`.
- Старі скрипти без `customer_id` отримують відповідь, що клієнт не увійшов.
- Без клієнта в сесії не працює жоден клієнтський інструмент; працює лише
  пошук у документації.
- Перевірено, що жоден оверлей промпту чи дефект у `app/agent/tools.py` не
  покладається на id клієнта з тексту чи на доступ до даних іншого клієнта:
  D04 і D12 переходять лише між рахунками того самого клієнта.
